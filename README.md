# 🎲 家事ルーレット

「今日、何の家事をやろう？」を考える手間をなくし、ルーレットに決めてもらうWebアプリです。

**公開サイト**: https://housework-roulette.vercel.app/



## 1. アプリの概要

家事を「自分で選ぶ」のではなく、**今使える時間**と**今日のコンディション**に合わせて、ルーレットが家事を1つ提案してくれます。提案された家事はそのままタイマーで計測でき、終わったら履歴に残ります。ゲーム感覚で取り組めることを目指しています。

### 主な機能

| 機能 | 内容 |
| --- | --- |
| ルーレット | 使える時間（5〜60分以上）とコンディション（元気〜かなり疲れた）に合う家事を重み付きランダムで抽選。気に入らなければ「もう一度回す」 |
| タイマー | 00:00から数え上げるストップウォッチ。一時停止・再開・中止ができ、所要時間の目安に達するとアラームが鳴る |
| 履歴 | 完了した家事と実際にかかった時間を日付ごとに確認できる |
| 家事リスト | 自分用の家事を追加・編集・削除できる。追加した家事はルーレットにも反映される |
| 今日の達成度 | 完了画面で、その日に終えた家事の件数を確認できる |

### ルーレットの抽選ルール

抽選ロジックは `src/lib/roulette.ts` にあり、`tests/unit/roulette.test.ts` でテストしています。

- **時間フィルタ**: 選んだ時間以内でできる家事だけが候補になる。例えば「5分」なら5分以内の家事のみで、10分の家事は絶対に出ない。候補が0件のときは、最も所要時間の短い家事にフォールバックする
- **コンディション×難易度**: 疲れているほど簡単な家事が、元気なほど大変な家事も出やすくなる
- **直近実施ペナルティ**: 直近5件の履歴に含まれる家事は出にくくなる（完全には除外しない）
- **連続回避**: 「もう一度回す」では、直前に出た家事を除いて再抽選する

つまり「時間内に収まる家事の中で、コンディションに合うものほど出やすいが、何が出るかは分からない」という仕様です。

## 2. 対象とするユーザー

- 家事に取りかかるまでが億劫で、「何からやるか」で迷ってしまう人
- 忙しい日と余裕のある日で、こなせる家事の量が変わる人
- 家事をゲームのように楽しみながら習慣にしたい人
- スマートフォンからサッと使いたい人（下部ナビ・タッチ操作に最適化しています）

ユーザーごとにアカウントが分かれており、家事リストや履歴は他の人と共有されません。一人暮らしの方はもちろん、家族がそれぞれのアカウントで使うこともできます。

## 3. 使用方法

1. **ログイン**: ユーザー名とパスワードでログインします。初めての方は「新規登録」から登録してください（ユーザー名は3〜30文字で文字種の制限なし、パスワードは8文字以上）。登録すると、初期の家事10件が自動で用意されます。
2. **条件を選ぶ**: ホーム画面で「使える時間」と「今日のコンディション」を選び、ルーレットを回します。
3. **家事を決める**: 表示された家事を「これをやる」で決定するか、「もう一度回す」で引き直します。
4. **タイマーで実施**: STARTを押すとカウントアップが始まります。一時停止・再開もできます。所要時間の目安に達するとアラームが鳴りますが、カウントは止まりません。
5. **完了**: 家事が終わったら「完了」を押します。完了画面が表示され、実際にかかった時間が履歴に記録されます。

下部のナビゲーションから、「家事リスト」で家事の追加・編集・削除、「履歴」で日付ごとの実績確認ができます。

## 5. データベース

開発・本番ともに **Neon（サーバーレスPostgreSQL）** を使い、**Prisma** で操作します。スキーマは `prisma/schema.prisma` にあります。

### テーブル構成

```
User (1) ──< HouseworkTask (N)
  │                 │
  └──< HistoryEntry (N) >── (家事への参照。家事が消えても履歴は残る)
```

| モデル | 役割 | 主な項目 |
| --- | --- | --- |
| `User` | ユーザー | `username`（重複不可）、`passwordHash`、`name`（表示名・任意） |
| `HouseworkTask` | ユーザーごとの家事 | 家事名、所要時間（分）、難易度（1〜5）、カテゴリ、説明、`isActive` |
| `HistoryEntry` | 完了した家事の履歴 | 家事名、所要時間、完了日時 |

設計のポイント:

- **論理削除**: 家事を削除しても `isActive = false` にするだけで、データは物理削除しません。
- **履歴のスナップショット**: 履歴には、実施時点の家事名・所要時間を保存します。後から家事を編集・削除しても、過去の履歴は変わりません。
- **ユーザー削除時**: ユーザーを削除すると、そのユーザーの家事と履歴もまとめて削除されます（カスケード削除）。
- **インデックス**: `userId` や `(userId, completedAt)` に付けて、履歴一覧などを速くしています。

### 接続方法

Neonのサーバーレス環境では接続数が増えやすいため、接続文字列を2つ使い分けます。

| 変数名 | 用途 |
| --- | --- |
| `DATABASE_URL` | アプリ実行用。コネクションプーリング経由（ホスト名に `-pooler` が付く方） |
| `DIRECT_URL` | マイグレーション専用。プーリングを通さない直接接続 |

### スキーマ変更の手順

1. `schema.prisma` を変更する
2. `npm run prisma:migrate` でマイグレーションを生成し、開発用DBに適用する
3. `prisma/migrations/` 配下のSQLをコミットする
4. 本番では `npm run prisma:deploy` で同じマイグレーションを適用する

## 6. セキュリティ

| 対策 | 内容 |
| --- | --- |
| パスワードの保護 | パスワードは平文で保存せず、bcrypt（ソルト付きハッシュ）で保存。ログイン時もハッシュ同士で照合する |
| セッション管理 | NextAuthのJWTセッションを `AUTH_SECRET` で署名。ログインしていないと家事・履歴の画面には入れず、ログイン画面に転送される（`src/proxy.ts`） |
| データの分離 | 家事・履歴の操作は、サーバー側で必ずログイン中のユーザーIDを取得して行う。更新・削除のクエリにも `userId` 条件を含めるため、他人のデータは見ることも変更することもできない |
| 入力値の検証 | ログイン・登録・家事の入力は、サーバー側でもZodで検証する（クライアント側の検証に頼らない） |
| 秘密情報の管理 | DB接続文字列や `AUTH_SECRET` は環境変数で管理し、`.env` は `.gitignore` 済み。`NEXT_PUBLIC_` を付けてブラウザへ公開しないこと |
| SQLインジェクション対策 | Prismaのクエリビルダー経由でDBにアクセスし、SQLを文字列連結しない |

## 7. 開発者向け情報

### セットアップ

```bash
npm install
cp .env.example .env   # DATABASE_URL・DIRECT_URL・AUTH_SECRETを設定する
npm run prisma:migrate # Neonのデータベースにテーブルを作成
npm run prisma:seed    # デモユーザー(demo / password1234)と初期家事を投入
npm run dev
```

`AUTH_SECRET` は `openssl rand -base64 32` などで生成してください。

### コマンド

| コマンド | 内容 |
| --- | --- |
| `npm run dev` | 開発サーバー起動 |
| `npm run build` | 本番ビルド |
| `npm run lint` | ESLint |
| `npm run typecheck` | 型チェック（`tsc --noEmit`） |
| `npm run test` | Vitestによるテスト実行 |
| `npm run quality` | lint → typecheck → test → build を通しで実行 |
| `npm run prisma:migrate` | 開発用DBにマイグレーションを作成・適用 |
| `npm run prisma:deploy` | 本番用DBにマイグレーションを適用 |
| `npm run prisma:seed` | デモユーザー・初期家事データの投入 |

### Vercelへのデプロイ

1. Neonでデータベースを作成し、プーリング接続文字列と直接接続文字列を発行する
2. Vercelの環境変数に `DATABASE_URL`・`DIRECT_URL`・`AUTH_SECRET` を設定する
3. `postinstall` で `prisma generate` が走るため、追加のビルド設定は不要
4. デプロイ前（または初回デプロイ後）に、本番の接続情報で `npm run prisma:deploy` を実行してテーブルを用意する（Vercelのビルドではマイグレーションを自動実行しない）
